================================================================================
ZYL FORMAL SPECIFICATION (v5.0)
"A Deterministic Lisp Systems Language with Region Inference, SSA IR, Actor
Concurrency, Capability-Based Safety, Traits, Generics, Explicit Closures,
ADTs, Testing Framework, Package Management, Structs, Aliases, RAII,
and Result-Based Error Handling"

================================================================================
0. CORE DESIGN PRINCIPLES (NORMATIVE)
================================================================================

P1. Determinism
    Same source program + same inputs → identical observable outputs and binaries.

P2. Safety
    No undefined behavior exists. No use-after-free, no data races, no nulls.

P3. Explicit Effects
    All effects (mutation, IO, FFI, concurrency) are statically trackable.

P4. Region-Based Memory
    Memory assigned via static region inference (Stack, Heap, Global, Circular, Pin).
    No manual allocation; no garbage collector for Stack/Heap (region-based reclamation).

P5. Strict Evaluation
    Evaluation order is deterministic and strictly left-to-right.

P6. Phase Isolation
    Compilation phases are strictly ordered (Parsing → Macro Expansion → 
    Type Inference → Region Inference → Monomorphization → ICNF → Codegen).

P7. Inference Over Annotation
    If the compiler can prove it, the programmer does not write it.
    Syntax exists only where inference cannot decide.

P8. Optional Layers Do Not Interfere
    Contracts, recovery, and testing frameworks never alter core semantics.

P9. Testability
    Testing is a core language built-in. Tests define behavior and drive implementation.

2. ABSTRACT SYNTAX (AST)
================================================================================

Expr :=
    Atom
  | (Op Expr*)
  | (def Name Expr)
  | (defn Name (Params*) Body)   ; also 'defun'
  | (let (Name Expr) Body)
  | (let-mut (Name Expr) Body)
  | (if Expr Expr Expr)
  
  ;; Error Handling (Result-based)
  | (try Expr (catch Name Expr))
  | (match Expr (Variant Pattern Body)*)
  
  ;; Concurrency & FFI
  | (spawn Expr)
  | (send Expr Expr)
  | (ffi-call String Expr* Integer)
  | (ffi-pin Expr)
  | (ffi-unpin Expr)
  
  ;; Control & Flow
  | (assert Expr String)
  | (while Expr Expr)
  | (for (Name [Expr]*) Expr Expr)
  | (cond Clause*)
  | (begin Expr+)
  | (error String)
  | (unwrap Expr)
  
  ;; Trait & Type System
  | (trait Name (TraitMethod*) TraitBound?)
  | (impl TraitName TypeName (ImplBody*))
  | (deftype Name (Variant*) VariantBound?)
  
  ;; Structs & Aliases
  | (defstruct Name (Field*) (:derive [Trait*])?)
  | (defstruct+ Name (Field*) (:derive [Trait*])?)
  | (alias Name TypeExpr)
  | (derive Name [Trait*])
  | (struct-get Expr FieldName)
  | (make-Name Expr*) ; Auto-generated constructor (e.g., make-Point)
  
  ;; Resource Management
  | (with-resource (Name Expr) Body)
  
  ;; Testing
  | (test-suite String (TestOrSuite*) (:keyword Value*)*)
  | (test String Body (:keyword Value*)*)
  | (assert-equal Expr Expr)
  | (assert-fail Expr String?)
  | (assert-true Expr String?)
  | (assert-false Expr String?)
  | (test-property String Generator PropertyFn)
  | (setup Body+)
  | (teardown Body+)
  | (run-tests (:keyword Value*)*)
  | (test-compile Expr (:expect-error Bool)?)

Field := (Name TypeExpr)
Generator := gen-int | gen-bool | gen-string | gen-float
PropertyFn := (fn (Param+) Expr)
Param := Name | (Name Type)
Clause := (Expr Expr)
TraitMethod := (Name (Param*) TypeExpr)
ImplBody := (defn Name (Params*) Body)
Variant := (Name TypeExpr*)
BaseType := Int | Float | Bool | String | Unit | Name

Evaluation: Strict left-to-right.

3. VALUE MODEL
================================================================================

Value V :=
    Int64 | UInt64 | Float64 | Bool | String
  | Tuple(V*)
  | Closure(Environment, Expr, CaptureMap)
  | ActorRef(ID)
  | Address(Region, ID)
  | StructValue(Name, Map<Name, V>)
  | ResultValue(Ok V | Err String)
  | Unit

CaptureMap:
    Maps captured variable names to inferred regions/capabilities (compile-time only).

StructValue:
    Immutable aggregate. Fields cannot be mutated in place.
    Mutation requires rebinding the entire struct instance.

ResultValue:
    Represents success (Ok) or failure (Err).
    'error "msg"' returns (Err "msg").
    'try' is sugar for matching on Result.

4. TYPE SYSTEM
================================================================================

4.1 Primitive Types:
    Int | Float | Bool | String | Unit

4.2 Composite Types:
    Vec<T>   — contiguous array (O(1) access, deterministic iteration if sorted)
    Map<K,V> — hash map (deterministic iteration by sorted key hash)
    Result<T, E> — error handling type
    Struct   — named collection of fields (immutable by default)
    Alias    — transparent wrapper (zero-cost)

4.3 Capability Types:
    TCap<T>     immutable shared access
    TMut<T>     exclusive mutable ownership
    TAtomic<T>  atomic shared mutation
    TBox<T>     heap-managed allocation
    TPin<T>     FFI-pinned memory (non-moving arena)

4.4 Function Types:
    TFun([T*], TReturn)

4.5 Trait Bounds:
    T : TraitName

4.6 Inference:
    Hindley-Milner with region/capability constraints.
    Monomorphization during Phase 5.

4.7 Type Equality:
    Structural for primitives/collections.
    Nominal for Structs/ADTs/Aliases.
    Aliases are transparent: A is coerced to B (and vice versa) without runtime cost.

4.8 Soundness (normative):
    A program the compiler accepts never uses a value at the wrong
    representation: no Int used as a pointer, no Float through integer
    arithmetic, no String compared by address, no call with the wrong
    number of arguments. The checker is sound, not best effort: every
    unification failure, occurs-check failure and type it cannot
    determine is a compile error, all of a program's type errors are
    reported, and then the compile fails.
    There is no cast form. The trusted base is the compiler, the C
    runtime, the runtime-signature table (stdlib/compiler/ffi_sigs.zyl)
    and a program's own extern declarations (§16).
    Known exception: `receive` returns a value of any type, because an
    actor mailbox holds whatever any sender put there (§15). Typed
    single-sender channels are to replace mailboxes and remove it.
    ZYL_STRICT_TYPES=report prints the errors as W_TYPE_STRICT warnings
    and continues; it is a tool for counting, never a way to run an
    ill-typed program.

4.9 Typing Rules (normative):
    Γ ⊢ e : τ. Top-level functions are generalized per strongly
    connected component of the call graph; local let bindings are
    monomorphic. A type variable left unconstrained is a type parameter.

    Literals        integer : Int   float : Float   true, false : Bool
                    "..." : String   unit : Unit
    Variable        Γ(x) = ∀ā.τ  ⊢  x : τ[ā := fresh]
    let             e1 : τ1,  Γ,x:τ1 ⊢ e2 : τ2  ⊢  (let x e1 e2) : τ2
                    (let-mut the same)
    set!            x bound by let-mut at τ,  e : τ  ⊢  (set! x e) : Unit
    begin           (begin e1 ... en) : type of en;  (begin) : Unit
    if              c : Bool,  a : τ,  b : τ  ⊢  (if c a b) : τ
                    c : Bool,  a : Unit  ⊢  (if c a) : Unit
    cond            every test : Bool, every body : τ.  A clause whose
                    test is the literal true or `else` ends the cond, and
                    the cond is τ; with no such clause, τ = Unit.
    while, for      condition : Bool  ⊢  the loop : Unit
    fn              Γ,x1:T1..xn:Tn ⊢ body : R  ⊢  (fn (x1..xn) body) : (T1..Tn) -> R
    Application     f : (T1..Tn) -> R,  ai : Ti  ⊢  (f a1..an) : R
                    (the argument count must equal the parameter count)
    Arithmetic      + - * / %: both operands Int -> Int, or both Float ->
                    Float (a closed class; no implicit conversion).
                    (- x) negates; (+ x) and (* x) are x.
    Ordering        < > <= >=: two operands of one type, Int, Float,
                    String or a declared ADT/struct (structural,
                    field by field)  ->  Bool
    Equality        = == !=: two operands of one type -> Bool
                    (structural for ADTs and Strings)
    Bits            bit-and bit-or bit-xor shl shr ashr bit-not: Int
    Constructor     for (deftype T (C F1..Fn) ...): C : ∀ā. (F1..Fn) -> (T ā),
                    ā the type parameters.  An untyped struct field is an
                    implicit type parameter of its struct.
    match           scrutinee : T ā; an arm (C x1..xn body) binds xi at
                    C's i-th field type; every body : τ  ⊢  match : τ.
                    Patterns are flat (E_NESTED_PATTERN); exhaustiveness
                    is §12.
    struct-get      p : S ā, f a field of S  ⊢  (struct-get p "f") : its type
    try             b : τ,  x : String ⊢ h : τ  ⊢  (try b (catch x h)) : τ
    Assertions      assert-true, assert-false, assert: a Bool -> Unit;
                    assert-equal l r: l and r of one type -> Unit
    print           any value -> Unit
    Traits          A method's Self is its receiver's type:
                    (trait Ord (compare (self (other Self)) Int)).
                    (Tr.m r a..): r's type selects the impl at compile
                    time; a trait-generic function is specialized per
                    type at every call and every use as a value; a call
                    whose receiver type stays unknown is E_CANNOT_INFER.
    exit, error     do not return: any type
    main            () -> Int
    Actors          spawn : Actor;  actor-self : Actor;
                    send : Actor a -> Unit;  receive : a (§4.8)
    FFI             a runtime symbol (zyl_*) has the type in the
                    signature table; a foreign symbol the type of its
                    (extern "sym" (T1..Tn) R) declaration (§16);
                    (ffi-pin v) has v's type.
    file-open       path : String, mode a literal fopen mode -> Int

4.10 Type Errors:
    E_TYPE_MISMATCH   two types that must be equal are not
    E_INFINITE_TYPE   a type would contain itself (occurs check)
    E_CANNOT_INFER    a type the program does not determine
    E_UNBOUND_VARIABLE a name defined nowhere

================================================================================
6. GENERICS
================================================================================

6.1 Generic Function Declaration:
    (defn name ((TypeParam : TraitBound*) (param Type) ...) body)
    (defun is a synonym.) TypeParam is an uppercase identifier (convention).
    TraitBound is optional; if absent, the type parameter is unbounded.
    Multiple bounds: ((T : Ord Eq)) requires T to implement both Ord and Eq.

    Multiple type parameters are declared as multiple parameter groups,
    each starting with an uppercase identifier:
        (defn pair ((T) (U)) (make-tuple t u))      ; 2 type params
        (defn min ((T : Ord) a b) ...)               ; 1 bounded type param
        (defn f ((T) (U) x Int) ...)                 ; type params may be
                                                     ; interleaved with typed
                                                     ; value parameters

    Scope: TypeParam is scoped to its own defn. T in one function does
    not leak into another. Shadowing T in a nested defn is an error.

6.2 Type Param Semantics:
    - Type parameters are positional (declaration order), but monomorphized
      naming is order-independent (see 6.4).
    - A type parameter used multiple times (e.g. (deftype Pair (Make T T)))
      constrains both fields to the SAME concrete type at instantiation.
    - Type parameters appear ONLY in type position:
        * as a variant field type:   (Some T)
        * as a function param type:  (defn unwrap ((T) opt T) ...)
        * in collection types:       Vec<T>, Map<K,V>
    - A type parameter cannot be used as a runtime value.

6.3 Generic Type in Collections:
    Vec<T>, Map<K,V>. T, K, V are inferred from usage context.

6.4 Monomorphization:
    For each call site of a generic function, the compiler:
    1. Infers concrete types for ALL type parameters from argument types.
       A single call site fixes every parameter it touches; a parameter
       with no evidence at any call site is an error (E_CANNOT_INFER)
       unless it carries a trait bound that selects a finite set.
    2. Verifies all trait bounds are satisfied by the concrete types
       (E_TRAIT_BOUND_NOT_SATISFIED otherwise).
    3. Generates a specialized function with canonical name:
           functionName_Type1_Type2_...
       Types are sorted alphabetically by type name (deterministic).
       f<Int, String> and f<String, Int> produce the SAME canonical name.
       Distinct type maps always produce distinct names.
    4. Caches the monomorphized function for reuse at other call sites
       with identical concrete types.

    Examples:
        (min 3 5)       → min_Int
        (min "a" "b")   → min_String
        (pair 1 "hi")   → pair_Int_String
        (pair 1.0 2.0)  → pair_Float

6.5 Generic ADTs:
    (deftype Option (Some T) None)
    (deftype Result (Ok T) (Err E))       ; 2 type params, collected from
                                          ; uppercase variant fields
    (deftype List (Cons T (List T)) None) ; recursive generic reference

    Semantics:
    - Option<Int> and Option<String> are distinct types.
    - Type parameters are collected from uppercase field names in variant
      declarations; duplicates are kept once (same-type constraint, 6.2).
    - Monomorphization applies to ADT constructors and pattern matching
      on generic ADTs.
    - Generic structs (defstruct with uppercase field types) are NOT
      supported; only ADTs and collections may be generic. (limitation,
      not a design goal)

6.6 Generic ADT Derivation:
    (derive Result [Eq])  ; requires ALL type parameters to implement Eq.
    Deriving on a multi-param ADT is allowed; the derived impl is
    parameterized over the ADT's type parameters. Error E_TRAIT_NOT_DERIVABLE
    if any concrete instantiation fails the field constraint.

6.7 Error Cases:
    E_CANNOT_INFER                — generic param with no call-site evidence
    E_TRAIT_BOUND_NOT_SATISFIED   — concrete type violates a bound
    E_UNKNOWN_GENERIC_PARAM       — reference to an undeclared type parameter
    E_TRAIT_NOT_DERIVABLE         — derive constraint fails

9. REGION SYSTEM (CORE MEMORY MODEL)
================================================================================

Regions R:
    Stack | Heap | Global | Circular | Pin

9.1 REGION RULES (DETERMINISTIC)
R1. Local stack allocation: If variable does not escape → Stack.
R2. Escape allocation: If returned, captured by escaping closure, or sent to actor → Heap.
R3. Actor transfer: spawn/send requires Send-capable type.
R4. FFI rule: ffi-call requires Pin region AND FFI_Pinnable type.
R5. Closure capture promotion: Escaping closure captures promoted to Heap.
R6. Cyclic structures: Cyclic references detected among heap values → Circular region.
R7. Global Region: Immutable constants only. Eager initialization. No mutation allowed.
R8. Pin Region: Non-moving arena. Values physically copied here for FFI. Never compacted.

9.2 EXPLICIT REGIONS (with-region)
Syntax:
    (with-region (arena :block B :align A :limit L) body)
    (with-region (fixed :size S :align A) body)
Kinds (closed set):
    arena: grows in blocks of B bytes (multiple of 4096, ≤ 64 MiB), at most L bytes in total (L = 0: no limit).
    fixed: exactly S bytes.
    A: power of two, 8 ≤ A ≤ 4096. Default 8.
Semantics:
    Allocations in body are placed in the region; the region is released when body ends.
    Exhaustion depends only on the request sequence (deterministic).
Errors:
    Malformed spec → E_REGION_SPEC (compile-time).
    Region exhausted → E_REGION_EXHAUSTED (runtime, catchable).
    Value of the region reaching body's result or any longer-lived location → E_REGION_ESCAPE (compile-time).
    (bytebuf Stack N) returned, stored, sent, or passed where it may be retained → E_REGION_ESCAPE (compile-time).

================================================================================
10. MUTABILITY AND ALIASING
================================================================================

Invariant:
    For any memory location:
        either exactly one TMut reference
        OR any number of TCap references

Violation: E_MUT_CONFLICT (compile-time error)

Struct Mutability:
    Fields defined in `defstruct` are immutable by default.
    To "mutate" a struct, the binding must be `let-mut`, and the entire struct
    must be rebound to a new instance: (set! p (make-Point new-x old-y)).
    Direct field mutation (set! (struct-get p x) 5) is FORBIDDEN.

Alias Transparency:
    Aliases are zero-cost. No runtime unwrap needed unless explicitly called.

================================================================================
11. EVALUATION SEMANTICS (BIG-STEP)
================================================================================

Judgment:
    ⟨E, Σ⟩ → ⟨V, Σ'⟩

State:
    Σ = ⟨H, S, R, A, F, M⟩

Evaluation order:
    STRICT LEFT-TO-RIGHT

Function application:
    evaluate function then arguments sequentially.

Closure application:
    (Closure(env, body, captures), args):
        env' = env ∪ bind(params → args)
        captures' = resolve captured variables
        evaluate body under env' with captures'

Test execution:
    Registration: (test-suite ...), (test ...)
    Execution: (run-tests ...)
    Isolation: Fresh environment per test.
    Parallel: Default parallel execution (deterministic ordering enforced).

================================================================================
12. CONTROL FLOW
================================================================================

12.1 IF:
    if true branch else branch

12.2 TRY/CATCH (Result Sugar):
    (try Expr (catch Name Expr))
    Semantics:
        1. Evaluate Expr.
        2. If Result is Ok(v), return v.
        3. If Result is Err(e), bind e to Name and evaluate catch body.
        4. Type of whole expression is Type of Ok branch AND Catch branch (must match).

12.3 MATCH:
    Matches variants in order. Exhaustiveness enforced at compile-time.

12.4 ASSERT:
    if condition false → runtime error E_ASSERT_FAIL

12.5 WHILE:
    (while condition body)
    Strict left-to-right. No termination detection (Halting Problem).

12.6 FOR:
    (for (init-bindings) condition body)
    
    init-bindings: list of (name [value]) pairs, written as S-expressions:
    - (name) — use existing variable (while-like)
    - (name value) — new binding with initial value
    - (name1 value1 name2 value2 ...) — multiple variables
    - () — empty, pure while loop
    
    Examples:
    (for () (< counter 5) (begin (print counter) (set! counter (+ counter 1))))
    (for (i 0) (< i 5) (begin (print i) (set! i (+ i 1))))
    (for (i 0 j 10) (< i 5) (begin (print i j) (set! i (+ i 1)) (set! j (+ j 1))))
    
    Condition: Boolean expression. Evaluated each iteration; loop exits when false.
    Body: begin-block containing loop actions. User must update loop variables via set!.
    Semantics:
    1. Evaluate init-bindings: create bindings or use existing variables.
    2. Evaluate condition. If false, exit loop.
    3. Execute body.
    4. Goto step 2.

12.7 COND:
    (cond (condition-1 body-1) ... (else body))

12.8 BEGIN:
    (begin expr-1 ... expr-n)

12.9 WITH-RESOURCE:
    (with-resource (Name Expr) Body)
    Semantics:
        1. Evaluate Expr to acquire resource R.
        2. Bind Name to R.
        3. Evaluate Body.
        4. On exit (normal or error), call (close R) or Drop trait method BEFORE propagating error.
        5. Returns value of Body (or propagates error).

12.10 ERROR:
    (error msg) returns (Err msg). Does not throw.

16. FFI MODEL
================================================================================

(ffi-call name args timeout)

(ffi-pin Expr)
(ffi-unpin Expr)

Timeout:
    name is a string literal; timeout is a positive integer literal in
    milliseconds (Compile Error E_FFI_SYMBOL_REQUIRED / E_FFI_TIMEOUT_REQUIRED).
    A foreign call that has not returned within timeout raises E_FFI_TIMEOUT.
    The foreign code is abandoned, never interrupted: memory it was handed
    stays valid for the rest of the process.
    A timeout is an FFI result (§27): observable external input.

Signatures:
    (extern "name" (T1 ... Tn) R)
    declares the C signature of a foreign symbol; every ffi-call to it is
    type-checked against it (§4.9), and an ffi-call to a foreign symbol
    with no extern is a Compile Error (E_CANNOT_INFER). The types are
    concrete (no type variables: that would be a cast) and fit a machine
    word: Int, Bool, String, Ptr, the runtime's opaque handle types, and
    (Fn (A1 ... An) R) for a C callback. Float is not allowed (the timed
    call passes every argument in an integer register), nor is Float
    returned. R may be Unit. Runtime symbols (zyl_*) are typed by the
    compiler's signature table instead; those that read raw memory or
    reinterpret a machine word may only be named by the standard library
    (E_FFI_RESTRICTED).

FFI_Pinnable types:
    Int, Float, Bool, String, Vec<T> (where T is FFI_Pinnable),
    and types composed solely of FFI_Pinnable types.

Pin Semantics:
    ffi-pin copies value to Pin Region (non-moving).
    Returns stable pointer.
    Pin lifetime tied to FFI call scope unless manually managed.
    ffi-unpin explicitly frees pinned memory.

20. NUMERIC MODEL
================================================================================

20.1 Integers:
    Int64 signed. Overflow behavior: checked (default), wrapping, saturating.

20.2 Floats:
    IEEE-754 binary64.

20.3 Division by Zero:
    Int -> E_DIVISION_BY_ZERO. Float -> ±Infinity/NaN.

20.4 Determinism:
    Bit-level reproducibility guaranteed.

22. COMPILATION PIPELINE
================================================================================

Phases (strict order):
    1. Parsing — Tokenize and parse to AST
    2. Macro Expansion — Expand macros (innermost-first, hygiene)
    3. Type Inference + Trait Resolution
       - Includes derive validation.
       - Validates struct field types and mutability.
       - Validates alias targets.
    4. Region Inference + Capture Analysis
       - Assigns regions (Stack, Heap, Pin, etc.)
    5. Monomorphization (Alphabetical Determinism)
    6. ICNF Generation (SSA IR)
    7. Optimization (Safe only)
    8. Code Generation
    9. Linking
   10. Contract Injection (Optional)
   11. Hash Finalization

Rule: No phase may depend on a later phase.

================================================================================
24. MODULE SYSTEM
================================================================================

24.1 Module Declaration: (module module-name)

24.2 Importing:
    (use module-path { symbol })
    (use module-path { symbol => alias })
    (use module-path :unsafe { symbol })
    (use module-path *)

    module-path is one of:
        package:module   — a module inside a declared dependency
        package          — that dependency's root module
        module           — a module inside the current package

    A package name always contains '/', so the three forms never collide.
    `unsafe` is a reserved module name (E_PKG_RESERVED_MODULE): the lexer
    discards whitespace, so `pkg :unsafe` and `pkg:unsafe` are one token
    stream and the marker must win.

    Naming a package absent from the manifest is E_PKG_UNDECLARED_DEP.

24.3 Exporting: `pub` at the definition site. (export symbol) is
    deprecated; the keyword remains reserved.

24.4 Visibility: two levels.
    Default — visible throughout the defining package, invisible outside.
    pub     — visible to any package that declares this one as a dependency.

    Importing a non-pub symbol is E_PKG_PRIVATE_SYMBOL. Visibility governs
    reachability only: every definition, public or not, receives a unique
    mangled symbol (§31.2), so renaming a private definition can never
    break a consumer.

24.5 Resolution: DAG-based at both levels. Modules within a package must
    form a DAG (E_MODULE_CYCLE); packages must form a DAG (E_PKG_CYCLE).
    Dependencies are declared in zyl.pkg (§31.3).

24.6 Crate Boundaries: coherence is checked over the whole resolved graph.
    Orphan rule: a package may implement a trait for a type only if it
    defines the trait or defines the type (E_PKG_ORPHAN_IMPL).

25. STANDARD LIBRARY (ABSTRACT)
================================================================================

Core modules:
    core: identity, compose, arithmetic, bool, type-predicates, I/O
    collections: Vec, Map (deterministic iteration)
    option: Option (Some, None), is-some, unwrap, map
    result: Result (Ok, Err), is-ok, unwrap, map
    io: file-open, file-read, file-write, file-close
    atomic: load, store, add
    actor: spawn, send, receive
    ffi: ffi-call, ffi-pin, ffi-unpin
    testing: test-suite, test, assert-*, test-property, run-tests

All obey region + capability rules.

The standard library is implicit: it needs no manifest entry, and its
version is the compiler's version, recorded in the lock (§31.6). Each
stdlib module declares the capability it provides, which is how §31.9
enforces capability grants at import time.

================================================================================
26. IMPLEMENTATION CONTRACT
================================================================================

Compiler MUST:
    - preserve evaluation order (strict left-to-right)
    - enforce aliasing invariants (TMut vs TCap)
    - enforce region rules (no escape violations)
    - enforce FFI safety (Pin region only)
    - enforce deterministic ICNF and monomorphization
    - enforce macro hygiene
    - enforce trait coherence (one impl per Trait-Type)
    - enforce match exhaustiveness (Compile Error if missing)
    - enforce defstruct immutability (no in-place mutation)
    - enforce alias transparency (zero-cost)
    - generate correct derive impls or raise E_TRAIT_NOT_DERIVABLE
    - ensure with-resource closes before error propagation

Compiler MAY:
    - optimize code (within semantics)
    - inline functions
    - remove dead code
    - refine escape analysis

Compiler MUST NOT:
    - reorder side effects
    - violate determinism
    - bypass region system
    - relax trait coherence
    - mutate struct fields without rebinding

================================================================================
27. DETERMINISM CONTRACT
================================================================================

Observable behavior includes ONLY:
    - return values
    - explicit IO
    - actor outputs
    - FFI results
    - runtime errors

NOT observable:
    - timing
    - memory layout
    - scheduling
    - register allocation

Guarantee: same program + same inputs → identical observable outputs and binaries.

For a package build, "same program" means the same resolved graph. Version
selection (§31.5) is a pure function of the manifests in the graph, and hash
finalization takes the graph hash as an input (§31.12), so two machines with
the same zyl.pkg, the same zyl.lock and the same compiler produce identical
binaries. Network access is confined to `zyl fetch`; builds are offline.

================================================================================
31. PACKAGE SYSTEM
================================================================================

Normative. Rationale, alternatives considered and the phased implementation
plan live in docs/package-management-design.md.

31.1 PACKAGE IDENTITY
--------------------------------------------------------------------------------
Name: a scoped path, two segments, for majors 0 and 1:  acme/json
For major N >= 2 the major is a third segment:          acme/json/v2

    Two majors are therefore distinct packages and may coexist in one graph.

Version: strict SemVer MAJOR.MINOR.PATCH, optional `-` pre-release suffix.
    SemVer ordering. A pre-release is selected only when some manifest in
    the graph names that exact pre-release.
    Major 0 is unstable: each minor is its own compatibility unit.

31.2 SYMBOL IDENTITY AND MANGLING
--------------------------------------------------------------------------------
Every top-level definition has a canonical key:

    <package>@<major>::<module-path>::<symbol>

    acme/json@1::json/parser::parse
    beta/xml@2::xml/parser::parse        (different package)
    acme/json@1::json/lexer::parse       (same package, different module)

Two packages may define the same name; so may two modules in one package.
The canonical key is also the sort key for monomorphization's alphabetical
canonical naming (§17), so ordering remains total over any graph.

Mangling MUST be injective. Lossy sanitizing (mapping every non-alphanumeric
byte to '_') is forbidden: it merges distinct keys.

    escape(b) = b             for [A-Za-z0-9]
              = "_5F"         for '_'
              = "_x" + HEX(b) otherwise, two uppercase hex digits

    mangle(key) = "zy_" + escape(package) + "_" + major
                        + "__" + escape(module) + "__" + escape(symbol)

    acme/json@1::json/parser::parse
      ->  zy_acme_x2Fjson_1__json_x2Fparser__parse

Over 200 bytes: truncate the prefix to 184 bytes and append 16 hex digits of
BLAKE3 over the full canonical key.

Monomorphized instances carry fully-qualified type arguments:

    acme/json@1::json::encode<acme/json@1::json::Node>
    acme/json@1::json::encode<beta/xml@2::xml::Node>

31.3 MANIFEST — zyl.pkg
--------------------------------------------------------------------------------
S-expression, read by the language's own lexer and parser.

    (package
      (name "acme/json") (version "1.4.0")
      (zyl "5.0") (edition "2026")
      (description "...") (license "...") (repository "...")
      (capabilities io)
      (deps
        (dep "core/bytes" "2.1.0")
        (dep "acme/utf8"  "1.0.0" (features utf16))
        (dep "acme/dev"   "0.3.0" (path "../dev"))
        (dep "acme/git"   "1.0.0" (git "https://..." (rev "a1b2c3d"))))
      (dev-deps (dep "acme/quickcheck" "2.0.0"))
      (features (feature utf16 (deps (dep "acme/utf16" "1.0.0")))
                (feature simd))
      (native (sources "c/fastpath.c") (cflags "-O2") (link-libs "m")))

    name, version, zyl, edition are required; all else defaults to empty.
    Requirements are bare versions; range operators are E_PKG_BAD_REQUIREMENT.
    Canonical serialisation: the order above, deps sorted by name.
    dev-deps never enter a dependent's graph.

31.4 COMPILATION MODEL
--------------------------------------------------------------------------------
Whole-program. Packages ship source; the resolver splices the full graph into
one compilation unit and monomorphizes globally. There is no ABI and no
binary-only distribution in v5.0. Build caching is keyed by content hash and
is sound by §27.

31.5 VERSION RESOLUTION — MINIMAL VERSION SELECTION
--------------------------------------------------------------------------------
    for each package P reachable from the root:
        selected(P) = max over all requirements R on P of version(R)

Each requirement is a minimum; the selection is the greatest minimum, within
a major. No search, no backtracking.

Consequences (all normative):
    - Resolution is a pure function of the manifests in the graph. It does
      not depend on index contents and does not drift.
    - Adding a dependency never silently upgrades an unrelated one.
    - Removing a dependency never silently downgrades another.

Upgrades are explicit: they rewrite a requirement in a manifest.

A root package or workspace MAY override a selection graph-wide:

    (overrides (override "acme/json" "1.9.2")
               (override "acme/bad" (path "../fork")))

Overrides never propagate from a dependency, and are recorded in the lock.

31.6 LOCK FILE — zyl.lock
--------------------------------------------------------------------------------
An integrity and provenance record, not a resolution input; deleting it does
not change which versions are selected.

    (lock
      (version 1)
      (compiler "5.0.0" (hash "blake3:..."))
      (pkg "acme/json" "1.4.0"
        (source (registry "https://github.com/zyl-lang/index"))
        (hash "blake3:...") (key "ed25519:...") (sig "ed25519:...")
        (features utf16) (capabilities io)
        (deps "core/bytes" "acme/utf8"))
      (capability-closure io ffi)
      (graph-hash "blake3:..."))

    hash               BLAKE3 over the canonical uncompressed archive (§31.7).
    key                publisher key, pinned on first use.
    capability-closure union of every capability granted in the graph.
    graph-hash         BLAKE3 over the canonical serialisation of the above.

Committed for applications and libraries alike. A library's lock constrains
its own CI, never its consumers.

31.7 CONTENT STORE AND CANONICAL ARCHIVE
--------------------------------------------------------------------------------
    zyl fetch   populates ~/.zyl/store/blake3/<hash>/ using git or curl.
    zyl build   reads the store only. Never networks. E_PKG_NOT_IN_STORE.

`zyl fetch` is the only command permitted to access the network.

Canonical archive (.tar.zst), so content hashes agree across producers:
    - paths relative to the package root, sorted bytewise
    - regular files and directories only; no symlinks, no devices
    - mode normalised to 0644 (files) / 0755 (directories)
    - all timestamps, uid and gid zero; user and group names empty
    - excluded: build/, .git/, zyl.lock, and any (exclude ...) patterns
    - zstd level 19, long-distance matching off

The recorded hash is over the UNCOMPRESSED canonical tar, so it does not
depend on the compressor.

31.8 INDEX AND TRUST
--------------------------------------------------------------------------------
The index is a git repository of S-expression metadata, sharded by name
(ac/me/acme/json.zyl). There is no server component.

    (index-entry (name "acme/json")
      (versions (v "1.4.0" (url "https://...tar.zst") (hash "blake3:...")
                   (key "ed25519:...") (sig "ed25519:...")
                   (zyl "5.0") (yanked false))))

Signing: the publisher signs the BLAKE3 hash of the canonical archive with
an Ed25519 key. Verification is MANDATORY and has no opt-out flag.

Trust on first use, per package:
    1. First resolution pins the publisher key into zyl.lock.
    2. Every later fetch MUST verify the signature against the pinned key
       and match the content hash.
    3. Key change is E_PKG_KEY_CHANGED; hash change is E_PKG_HASH_MISMATCH.
       Both halt the build until accepted explicitly, producing a lock diff.

Published versions are immutable. A yank is advisory: it affects new
resolutions only (E_PKG_YANKED), never an existing lock.

31.9 CAPABILITIES
--------------------------------------------------------------------------------
A package declares the capabilities it may use. Absent means none.

    (capabilities io)     ; may do IO; may not use FFI or spawn actors
    (capabilities)        ; pure computation only

    io      core/io and everything under stdlib/io
    ffi     ffi-call, ffi-pin, Pin-region allocation
    actor   spawn, send, receive
    secret  the Secret capability type and stdlib/math/secret
    native  shipping and compiling C sources (§31.10)
    unsafe  :unsafe imports

Enforcement runs after module resolution and before type inference. The
resolver tags every top-level form with its owning package; the pass rejects
a capability-bearing construct, or a `use` of a capability-bearing stdlib
module, from a package lacking the grant. Violations are
E_PKG_CAPABILITY_VIOLATION.

A declared set is a ceiling on the declaring package. It is not re-granted
per edge. The effective transitive closure is computed and written to the
lock; growth in the closure is reported by `zyl update` and is
E_PKG_CAPABILITY_GROWTH under --locked. A root package MAY forbid
capabilities graph-wide:

    (deny-capabilities ffi native unsafe)

31.10 FEATURES AND NATIVE DEPENDENCIES
--------------------------------------------------------------------------------
Features are additive-only: a feature MAY add top-level definitions and
trait impls, and MAY NOT remove or alter an existing one.

    (feature-gate utf16 (pub defn parse-utf16 (b) ...))

Valid at top level only. Because gated forms are separate definitions, the
additive property holds by construction: no feature can change an existing
signature. A gated definition colliding with a base definition is
E_PKG_FEATURE_COLLISION.

Features are unified: the union of all requests across the graph is
computed, the package is compiled once with that union, and the union is
recorded in the lock. Optional dependencies enter the graph only when their
feature is in the union.

Native dependencies are declarative. Build scripts are FORBIDDEN in any
form; arbitrary build-time code would forfeit §27.

    (native (sources "c/fastpath.c") (cflags "-O2" "-DJSON_STRICT")
            (link-libs "m") (include-dirs "c/include"))

    - requires the `native` capability; using the symbols requires `ffi`
    - paths are package-relative (E_PKG_NATIVE_PATH_ESCAPE)
    - cflags come from an allowlist: -O*, -D*, -std=*, a fixed -f subset.
      Raw -I, -L, -l and any -Wl, are rejected (E_PKG_NATIVE_FLAG_DENIED);
      includes go through include-dirs and linking through link-libs.
    - the toolchain invokes cc with a canonical sorted argument vector and
      records the object hash in the lock

31.11 WORKSPACES, EDITIONS, TOOLING
--------------------------------------------------------------------------------
Workspace root carries zyl-workspace.zyl:

    (workspace (members "stdlib" "selfhost" "tools/lsp") (overrides ...))

    One zyl.lock at the root, covering every member. One shared build cache
    and store. Members depend on one another by path and MUST still carry a
    version matching the target's manifest, so a member stays publishable.
    Under §31.5 a single root lock cannot skew between members.

Editions: (zyl "5.0") is a minimum compiler version (E_PKG_COMPILER_TOO_OLD).
(edition "2026") names the syntax era. Packages of different editions coexist
in one graph: each is parsed and lowered under its own edition's rules and
all converge on one ICNF. Unknown edition is E_PKG_UNKNOWN_EDITION. v5.0
defines exactly one edition: 2026.

Tooling — subcommands of the zyl binary:

    zyl new | add | fetch | build | test | update | vendor | audit
    zyl publish | key

31.12 DETERMINISM
--------------------------------------------------------------------------------
Hash finalization (pipeline step 11) takes, in this canonical order:

    1. the compiler's own hash
    2. graph-hash from the lock
    3. the canonical native-object hashes
    4. the ICNF hash

`zyl build` writes zyl.buildinfo beside the binary recording all four plus
the resolved graph in canonical form, so a third party can verify that a
binary was produced from a claimed set of inputs.

    - Same zyl.pkg + same zyl.lock + same compiler => identical binaries.
    - An index compromise cannot alter a build that has a lock.
    - Content-hash-keyed build caching is sound by §27.
